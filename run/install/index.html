Install the hub

The hub runs as one container. Before you start it, it needs a database, a speech-to-text server, two volumes, a certificate, and the address people will reach it by. It checks each of these as it starts, and refuses to start, naming the setting, when one is missing or wrong.

The image

Section titled “The image”

The image is built from the repository’s Dockerfile and published as ghcr.io/jdetmar/cairn-hub, tagged main and sha-<commit>. Pin your deployment to an image digest rather than a tag, so a restart never brings a hub you did not choose.

Inside the image, the hub reads its data from /data and its routes from /config/routes, and listens on two ports, 8080 and 8081.

The database

Section titled “The database”

The hub needs a PostgreSQL 17 database, which this guide calls cairn, owned by the role the hub connects as, so that the hub can apply its own migrations. Give the hub the connection string from your secrets, never from a file in the image:

As it starts, the hub applies each migration the database has not had yet. It refuses to start against a database that a newer hub has already migrated, so going back to an older image means restoring the database too; Backups, upgrades, and repairs says how.

The speech-to-text server

Section titled “The speech-to-text server”

The hub sends each recording to an OpenAI-compatible transcription endpoint, POST <url>/v1/audio/transcriptions, and asks GET <url>/health whether the server is up. speaches serves both, and runs faster-whisper on a CPU:

speaches only serves a model it has downloaded, so the second command downloads the model once; the volume keeps it across restarts. Then point the hub at the server and name the model:

EngineLabel is recorded with every note as the engine that transcribed it, so change it when you change the model. When the server is down, the hub holds each recording and tries again, so no note is lost; see Health and monitoring.

Volumes

Section titled “Volumes”
Path Holds
/data spool/, where each upload waits until it is transcribed and delivered; keyring/, the keys that keep people signed in across restarts; and destinations/, the files of logfile-v1 destinations
/config routes/, each person’s routes file
Where Cairn__Recordings__Dir points, such as /recordings Each recording kept for its owner to play, only once you turn keeping recordings on; an encrypted volume on a file system of its own, mounted at that folder, never inside /data

Keep each on a persistent volume, and in your backups. The recordings’ volume is needed only to keep recordings; turn keeping on only once it is encrypted and mounted, as The storage it needs says.

The hub tells a device it may delete a note from its card as soon as the upload is safely in the spool, so a spool that is lost before the note is transcribed loses that note.

The key ring’s certificate

Section titled “The key ring’s certificate”

The key ring in /data/keyring is encrypted with a certificate of your own, kept with your secrets and never in /data, so that a copy of /data alone cannot sign anyone in. Make one once; the hub never reads its dates, so it does not need renewing:

Mount the two files, at /secrets/keyring for example, and name them:

A new certificate cannot read the keys the old one encrypted, so replacing it signs everyone out, and the hub makes a new key and carries on.

The address people reach it by

Section titled “The address people reach it by”

People’s passkeys belong to the hub’s host name, so the hub must know it:

The origin is https and a host name, with a port if need be and nothing after it. It cannot be an IP address, since a passkey cannot belong to one; the one plain http origin the hub takes is http://localhost, for a hub on your own machine. The hub answers as this origin whatever a request’s Host header says, and every link it hands out starts with it. Open the hub’s pages at exactly this address, or passkeys will not work.

The hub serves plain HTTP; put a reverse proxy in front of it to serve HTTPS. Name the proxy, by its address or its network, so the hub believes the client address it forwards, which the hub’s per-address limits count by:

With no proxy named, the hub believes no forwarded header from anywhere, and every device seems to come from the proxy’s address.

Two ports

Section titled “Two ports”
Port Serves Who should reach it
8080 The API for devices, GET /v1/health, and the pages Your devices and people, through the proxy
8081 /livez, /readyz, and /healthz, and nothing else Only your orchestrator’s probes, and you

Leave 8081 out of anything that exposes the hub to your network. The hub answers the three health pages only on that port, and refuses to start if a public address uses it. Health and monitoring says what each page checks, and which to use for which probe.

Starting it

Section titled “Starting it”

With Docker, on a network shared with the speech-to-text container and a reverse proxy on the same machine, the whole hub is:

-e ConnectionStrings__cairn with no value passes the connection string on from your shell’s environment, so it stays out of your shell history. The last command makes the routes folder once.

When /config/routes is missing, the hub warns as it starts and holds every note back, with its audio in the spool, until the folder is there; an empty folder is fine, and means no one’s notes are delivered anywhere yet.

On Kubernetes, the same settings go in the Deployment’s environment, from a Secret for the connection string, the certificate, and any other secret. Expose only port 8080 through the Service and the Ingress, and probe port 8081 as Health and monitoring shows.
