Health and monitoring

The health pages

Section titled “The health pages”

The health pages are on the management port, 8081, which should be reachable only by your orchestrator and by you.

Page Checks Answer
/livez That the hub is running 200 with {"ok":true}
/readyz That the ingest ledger and the accounts can answer 200 or 503, with {"ok":...} and nothing else
/healthz Every check Each check’s name, status, how long it took, and a description, as JSON; 200 when healthy or degraded, 503 when unhealthy

Five checks report degraded at worst, so they show on /healthz but never make the hub unready, because none of them stops the hub taking a note: it keeps the note and retries when transcription or a delivery fails, files it whether or not its recording is kept, and takes it whether or not a warning goes out:

  • stt asks the speech-to-text server for GET /health, and gives it three seconds.
  • failures counts the transcriptions that failed and wait to be retried, and the notes whose delivery was given up on.
  • recordings, which is there only while keeping recordings is enabled or Cairn__Recordings__Dir is set, reports degraded while the recordings’ storage check has failed, keeping is enabled with no folder set included; while any recording was not kept in the last day, for want of room or as the copy failed; while a call to the recordings’ volume that missed its deadline is still running; while the volume cannot be listed within five seconds; while the sweep’s last pass failed; while the sweep could not sweep one or more people’s recordings in its last finished pass; or while the sweep has not finished a pass for two hours, counted from when the hub started or from its last finished pass, whichever is later. Unless the storage check has failed, when it says that alone, its description says when the sweep last finished a pass, in UTC, or that it has not run yet. It reports counts, never a note or a person.
  • quiet-devices watches the hourly check that logs a device as it turns quiet or lost: it reports degraded while its last pass failed, or while it has not finished a pass for two hours. A pass fails when the hub cannot read the devices, which usually means the database is down, and accounts already reports that as unhealthy; the next pass covers the hours the failed one missed.
  • battery-warnings, which is there only while the hub names an ntfy server, watches the check that sends low battery warnings every five minutes: it reports degraded while its last pass failed, while one or more people’s warnings could not be sent in its last finished pass, because the ntfy server did not take one or sending to them failed, which the next pass tries again, or while it has not finished a pass for ten minutes. With nothing to warn of, a pass sends nothing, so an ntfy server that is down shows here only once a warning is due.

recordings, quiet-devices, and battery-warnings each count from when the hub started or from their worker’s last finished pass, whichever is later, and each one’s description says when the worker last finished a pass, in UTC, or that it has not run yet, and when a failed pass failed. The sweep makes a pass as the hub starts, and the other two only after their first interval, so until then they say they have not run yet, which is healthy.

/healthz carries no stack trace and nothing from a request or a note. To read it on Kubernetes:

Devices use GET /v1/health on the public port, which answers as /readyz does, with no detail; a device that cannot reach a time server also reads the time from its Date header.

Probes

Section titled “Probes”

The hub does all its start-up work, migrations included, before it listens, so a 200 from /livez already means it has started.

Probe Page Timing
Startup /livez on 8081 Every 5 seconds, up to 24 failures, so a slow first start has two minutes
Liveness /livez on 8081 Every 20 seconds
Readiness /readyz on 8081 Every 10 seconds

Status, for a script

Section titled “Status, for a script”

GET /v1/status, with a reader token as a bearer token, reports how many notes there are, how many uploads wait to be transcribed or failed, and how many notes wait for a delivery or had their delivery given up on, under pendingProjections and deadProjections. A member’s token counts their own; an admin’s counts everyone’s. It also lists each of those people’s devices, with when each was last seen, its last upload and its outcome, its battery level, and whether it is quiet or lost. An admin’s token also reads the refused signatures since the hub started, by request and by reason.

The integrity check

Section titled “The integrity check”

integrity checks that each person’s notes were delivered, kept, or dropped as their routes say, and reports any that were not:

It reports a note whose delivery was given up on; one still waiting after Cairn__StaleHours, 6 by default, which means a webhook is failing or a routes file cannot be read; a note filed with no record of its changes, which is never delivered; an upload still waiting to be transcribed after the same time, which usually means the speech-to-text server is down; and a routes file that is not valid. Run it on a schedule, and look at anything it reports.

It also checks each person’s kept recordings, and adds them to that person’s report as Recordings: how many are kept, and each issue, by the kinds Checking them lists. Without --owner, a copy under a user id that has no account is reported under the key (no account), which no person’s name can be. A recordings issue makes it exit 1, as any other issue does.

Its exit code says how the check went:

Exit code Meaning
0 Every note and every kept recording it checked is as it should be
1 It found an issue, which it reports
Anything else It could not finish the check, such as 2 for an owner it does not know, or a database it cannot reach

Only 0 is good. A run that never starts, or never ends, gives no exit code at all, so alert both on a run that does not exit 0 and on no run having exited 0 for longer than your schedule allows.

Telemetry

Section titled “Telemetry”

The hub exports its traces, metrics, and logs over OpenTelemetry’s OTLP to wherever these settings say, and nothing when none is set:

Setting What it sends
OTEL_EXPORTER_OTLP_ENDPOINT All three, to the address it gives, under /v1/traces, /v1/metrics, and /v1/logs on http/protobuf
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT Traces, to exactly the address it gives
OTEL_EXPORTER_OTLP_METRICS_ENDPOINT Metrics, to exactly the address it gives
OTEL_EXPORTER_OTLP_LOGS_ENDPOINT Logs, to exactly the address it gives

With OTEL_EXPORTER_OTLP_ENDPOINT set, a signal’s own endpoint, where set, wins over it for that signal. Without it, only the signals that have an endpoint of their own are sent, so a receiver that takes metrics alone is sent metrics alone. OTEL_EXPORTER_OTLP_PROTOCOL is grpc unless set to http/protobuf, and OTEL_EXPORTER_OTLP_HEADERS and OTEL_EXPORTER_OTLP_TIMEOUT apply to every signal; each signal’s own, such as OTEL_EXPORTER_OTLP_METRICS_PROTOCOL, wins over them. OTEL_SERVICE_NAME names the hub in what it sends. Without the shared endpoint, the hub refuses to start when a signal’s own endpoint is not an absolute http or https address, or its own protocol is neither of the two, or its own timeout is not a positive number of milliseconds.

Each stage of a note is its own trace, the upload, the transcription, and each delivery, and every span of them carries cairn.event.id, so filtering on a note’s id follows it from end to end. The hub’s counters cover uploads taken, transcriptions, deliveries, dead deliveries, throttled uploads and joins, and refused signatures. Without any of the settings, nothing is exported, and the hub’s log is what shows a throttled device or a refused signature.

Metrics alone, to Prometheus

Section titled “Metrics alone, to Prometheus”

Prometheus takes metrics over OTLP, on http/protobuf alone, once its OTLP receiver is turned on with --web.enable-otlp-receiver. Give the hub its address and protocol, and name it:

By default, Prometheus turns each name’s dots into underscores, and adds the unit to a name that has one, so cairn.health is cairn_health, cairn.health.completed is cairn_health_completed_seconds, and the cairn.check dimension is the cairn_check label. The hub sends its metrics once a minute.

The health checks

Section titled “The health checks”

The hub runs each of its health checks on a period of its own, and reports each one’s last result as two gauges, with the check’s name, cairn.check, as their one dimension:

Instrument Unit What it reports
cairn.health None The check’s last result: 0 healthy, 1 degraded, 2 unhealthy
cairn.health.completed Seconds When the check last finished, in seconds since the Unix epoch

A check that stops being run keeps sending its last result, so cairn.health.completed is what shows it overdue. Sending them never runs a check: they report what the last run found. The checks are first run about five seconds after the hub starts.

Every check is run once a minute, but failures, recordings, and stt, which read every person’s records or call the speech-to-text server, are run every five minutes. A run that takes longer than its timeout, 30 seconds unless set, reports the check’s worst status, degraded or unhealthy, and the same timeout holds when /healthz runs it. The failures and recordings checks’ reads of the database are not cut short by it, so a run of either ends when they do, within the database’s command timeout, 30 seconds unless the connection string sets another. These settings change them, in whole seconds:

Setting Default What it is
Cairn__Health__PeriodSeconds 60 How often each check is run, but failures, recordings, and stt
Cairn__Health__TimeoutSeconds 30 How long a run of each check may take
Cairn__Health__Checks__<check>__PeriodSeconds 300 for failures, recordings, and stt How often that check is run
Cairn__Health__Checks__<check>__TimeoutSeconds None How long a run of that check may take

The hub refuses to start when one is below a second, or when <check> is not one of its checks.

Kept recordings

Section titled “Kept recordings”

Four instruments cover kept recordings, none of them with a person as a dimension:

Instrument Kind What it counts
cairn.recordings Counter Recordings the hub kept, or did not keep, by cairn.outcome: kept, not-kept-chosen, not-kept-no-room, or not-kept-copy-failed
cairn.refused_plays Counter Requests to play a recording that were refused
cairn.recording_deletions Counter Recordings deleted, by cairn.reason: due, unfiled, owner, or purge
cairn.recording_bytes Gauge The bytes kept, as the sweep’s last full pass summed them; a pass that could not count every person leaves it as it was

Their spans are cairn.recording.keep, one for each recording the hub tries to keep, inside the note’s transcription, which carries the note’s id as cairn.event.id; and cairn.recordings.sweep, one for each pass of the sweep, which carries how many recordings it deleted and how many copies it removed. A note’s id is on spans alone, never on a metric, and no metric has a person as a dimension.

Alerting

Section titled “Alerting”

The hub sends you no alert of its own. Your monitoring alerts on the metrics it sends, as it does for any other service, and you choose which alerts fire, after how long, and where they go. The hub also cannot tell you that its volume is full, or that it is down, so alert on those as you do for other services.
