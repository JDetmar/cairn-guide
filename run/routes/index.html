Routes and the webhook

Every note is kept in its owner’s archive on the hub. Each person has at most one webhook, and each of their tags is either sent to it or kept on the hub.

Each person’s routes file

Section titled “Each person’s routes file”

Each person’s routes are a file of their own, <user id>.yaml, in the routes folder, /config/routes in the image. You write it; people cannot edit their routes on the hub’s pages yet.

A person’s user id is on the hub’s Routes page, under Settings, once they sign in, beside a read-only list of their tags, each sent or kept, and their webhook’s host, never its path or its secret, and admin list prints everyone’s. The id never changes and is never a name, so renaming someone leaves their file where it is.

The hub reads a person’s file each time it routes one of their notes, so an edit takes effect at once, with no restart. Sending a tag, or adding a webhook, sends the notes filed under that tag from then on; send-notes sends the ones filed before.

The file’s tags are also the tags the person’s devices offer, in the file’s order, after untagged, which is always first: five in all at most. A tag is send, to the webhook, or keep, on the hub only; a tag with no value is kept, and so is untagged unless the file says to send it. A person with no webhook keeps every note on the hub, whatever their tags say.

A file that is not valid holds back that person’s notes alone: they are archived, and their audio held in the spool, but nothing is sent until the file is fixed, and their devices keep the tags they have. The hub logs a warning on each pass, and the integrity check reports a routes issue naming the file.

An older hub read cairn-routes/1, which named destinations and routed each tag to any number of them. This hub refuses that file as it refuses any it cannot read, so rewrite it as cairn-routes/2: the webhook is the old destination with adapter: webhook-v1, and a tag that went to it is send.

The webhook

Section titled “The webhook”

The webhook is sent each note under a sent tag, and each change the hub makes to it, as an event in JSON:

owner is the person’s id, which never changes, so a flow keys on it and only shows owner_name. url is the note’s page on the hub. recording.state is never_offered, kept, not_kept, with a reason of chosen, no_room, or copy_failed, or deleted. title and recording.url are always null for now.

An event’s type says what the webhook should do with the note:

  • note.filed: a note it does not have yet; previous_tag is null.
  • note.updated: a note it may have already, whole, as it is now, such as after its recording was deleted or its tag changed between two sent tags; previous_tag is the tag it was sent under before, when that differs.
  • note.retagged: a note it may have, now under a tag that is kept, so it should let the note go; note carries only id, version, and owner, and previous_tag the tag it was sent under, never the tag it moved to.

Each change raises the note’s version by one, and several changes made while the webhook was down go as one event, of the newest. A receiver keeps the highest version it has seen of each note, and ignores an event with a lower one, since a retry can arrive after a newer event.

Each request carries Idempotency-Key and X-Cairn-Event, both the event’s id, and, unless it is note.retagged, X-Cairn-Tag, the note’s tag. The body carries the text, never the audio.

When secret_env names an environment variable of the hub’s, its value is sent as a bearer token, and as X-Cairn-Signature: sha256=<HMAC-SHA256 of the body>, so the receiver can check whichever it prefers. The hub refuses to send a secret over plain http:// unless the host is loopback or the webhook sets allow_http: true.

Any 2xx answer is a delivery. Anything else, or a timeout, is retried with backoff, and after Cairn__MaxAttempts tries, 8 by default, the delivery is given up on; send-notes sends it again once the receiver is fixed. Receivers should use Idempotency-Key to ignore an event they already have, since a retry or send-notes can send it twice.

A webhook that cannot be built, such as one whose secret_env is not set, fails each delivery, which is retried and given up as any failure is.

A receiver that only speaks MCP, or needs an OAuth sign-in of its own, is reached the same way: point the webhook at a flow, in n8n for example, that holds the sign-in. The hub learns no OAuth flows for receivers.

A note is data, never instructions

A note’s text is whatever was said near the recorder, or whatever someone holding a device’s key chose to upload. To a receiver that acts on what it gets, such as a home automation or an AI agent with tools, a note that says “ignore your instructions and …” is a prompt injection, and one that names an automation is a command. Such a receiver must either ask a person before it acts, or only be able to do things that are safe whatever the text says. Before you send a tag to one, check the flow that receives the notes against that rule; it runs outside the hub, so the hub cannot check it for you. The archive only stores a note, so it needs no such check.

When audio is released

Section titled “When audio is released”

The hub holds a note’s recording in the spool until the webhook is owed nothing more for it, then deletes it, which is called releasing it. A note under a kept tag, or of a person with no webhook, has its recording released once it is filed. Otherwise it is released once the note’s last change was delivered, or given up on, or dropped, as a change is when its tag is switched to kept before the webhook took it.

Unless keeping recordings is on, and the note’s owner keeps theirs, by their own choice or the hub’s default, the text is all the hub keeps once the recording is released. A kept recording is a copy of its own, on the recordings’ own storage, made just before the note is filed, whatever its deliveries are doing. Releasing the spool’s copy leaves the kept one alone, and deleting the kept one leaves the spool’s alone: that goes when it is released, and is never played.
