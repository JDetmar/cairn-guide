Backups, upgrades, and repairs

What to back up

Section titled “What to back up”
What Why Can it be rebuilt?
The PostgreSQL database Every note, every account, device, and audit log entry, each person’s warning topic and choice of keeping recordings, and the record of each recording kept or deleted No, apart from its cache schema
The key ring’s certificate and key Without them the key ring cannot be read, and everyone is signed out No; keep it out of the backups of /data, since the two together can sign anyone in
/config/routes Each person’s routes Only by writing them again
/data The spool and the key ring The spool holds notes not yet transcribed, which the device may already have deleted
The recordings’ volume, if you keep recordings Each recording kept for its owner to play No: once a note’s spool file is released, the kept copy is the only one; see Recordings and restores
Your secrets The connection string, the provider’s client secret, the ntfy token, and the webhook key They can be made again, at the other end too

Back the database up at least daily, and keep a copy somewhere other than the machine it runs on. A nightly pg_dump loses at most a day of notes with a disk; archiving PostgreSQL’s write-ahead log, as CloudNativePG and similar operators do, loses almost none. Keep the backups as private as the notes themselves: they hold everything people said to their recorders, and who uses the hub and when.

Recordings and restores

Section titled “Recordings and restores”

Back the recordings’ volume up daily, as you do the database, and keep its backups encrypted, as the volume is. A recording deleted by its owner, the sweep, or recordings purge stays in those backups until they expire, so keep them no longer than you are willing to have a deleted recording last.

The database keeps a record of each deleted recording, which says when it was deleted and why, so each kind of restore leaves the recordings in a known state:

What you restore What it leaves
The recordings’ volume alone A deleted recording’s copy comes back, but its record still says deleted, so it is never played, and the sweep removes it at its next pass
The database alone, to before a deletion The recording’s record says kept again, but its copy is gone, so its note’s page says it is missing and integrity reports recording-missing
Both, to before a deletion The deletion is undone: the recording is kept, and its owner can play it again
The database alone, to before a recording was kept Its copy has no record, so the sweep leaves it, integrity reports recording-unmatched, and only recordings purge-unmatched deletes it

So a restore of the database to before a deletion undoes the deletion for as long as any copy of the recording remains, on the volume, in its backups, or in the spool. Going back after an upgrade is such a restore, of a dump taken just before the upgrade, so only what was deleted since then can come back; run integrity after one.

Running it again writes only the files that changed, and deletes nothing. The folder opens in Obsidian, and can go into a git repository of the person’s own. It is a copy for that person, not a backup of the hub: it has no accounts, no devices, and no deliveries.

Upgrading

Section titled “Upgrading”

Pin the hub to an image digest, and change it on purpose. A new image applies its database migrations as it starts, and migrations only go forward. An older image refuses to start against a database a newer one has migrated, so the way back from an upgrade is restoring the database as it was just before it.

Before an upgrade, make sure you can get that copy: take a pg_dump just before it, or note the time, if your backups can recover to a moment.

Repairs

Section titled “Repairs”

Resetting the cache

Section titled “Resetting the cache”

The cache schema holds the ingest ledger, which the hub can do without once each upload is archived. If it goes wrong, empty it:

It touches no account, no note, no delivery, and no audio, so nothing is sent again.

An upload that has not been archived yet is in no archive to rebuild it from, so while the ledger holds one, the reset changes nothing, and lists each with its owner and where its audio waits in the spool. Let the hub archive them first, or run cache reset --forget-unarchived to forget them, leaving their audio in the spool.

Delivering again

Section titled “Delivering again”

send-notes sends one person’s notes to their webhook again, such as when it lost what it had, or was away for a while:

It sends each of Kim’s notes under a tag their routes send, captured since --since when it is given, or every one when it is not, and each note whose delivery was given up on, whatever its tag or time. Each goes as its next delivery would: a note the webhook may have already goes as note.updated, under the id it was last sent with, so a receiver that has it can ignore it. A note with a change still waiting is left out, since the hub sends it at its next pass anyway. --dry-run lists the notes it would send, and sends nothing. It refuses a routes file that cannot be read, and a person with no webhook.

A key in the key ring that is not encrypted

Section titled “A key in the key ring that is not encrypted”

A hub that first ran an image from before the key ring was encrypted made a key in plain text, and the hub refuses to start while one is there, naming each such file in /data/keyring. Delete those files and start the hub again: it makes a new key, encrypted, and whoever signed in with the old one signs in again.
